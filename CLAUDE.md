# AI Research Paper Assistant

## Project Purpose
Portfolio project for backend/AI-engineering internship applications. Users upload research papers (PDF), and the system uses RAG (Retrieval-Augmented Generation) to summarize them, answer questions grounded in the paper's actual content, and explain difficult concepts at different depths.

**Bug found and fixed (during Phase 11 verification): `UploadedPaper.chat_sessions` (`app/models/uploaded_paper.py`) was declared with `cascade="all, delete-orphan"`. Deleting a paper that anchors a chat session cascade-deleted that session (and all its messages) at the ORM level — even a multi-paper (Phase 4) session with other papers still very much alive in the library — directly contradicting `delete_uploaded_paper`'s own docstring, which claims the anchor is set to NULL by the FK's `ondelete="SET NULL"` and the session survives. The ORM-level cascade was pre-empting that FK before it ever got a chance to apply. Fixed by dropping the cascade from that one relationship. Verified live with the exact failure scenario: created a session anchored on Paper A but also linked to Paper B (Phase 4 multi-paper), deleted Paper A, confirmed via direct DB query and the actual `GET /papers/{B}/chat/{session_id}` API call that the session survived with its anchor nulled, its link to Paper B intact, and both messages preserved.**

## Already Implemented (Phases 0-18 complete — do not rebuild, extend/harden instead)

### Backend (FastAPI, `backend/app/`)
- **Structure**: routers / models / schemas / services / auth / config / utils — keep using this pattern for all new code.
- **Auth**: JWT access tokens (PyJWT) + bcrypt (passlib), register/login/current-user, token blacklist table (`RevokedToken`) for logout. `app/auth/dependencies.py` has `get_current_user`.
- **DB migrations**: Alembic is set up and in use (migrated off `Base.metadata.create_all()` during Phase 0). Use `alembic revision` / `alembic upgrade head` for all schema changes going forward — do not add ad-hoc `create_all()` calls.
- **Secrets**: `.env` is gitignored, `JWT_SECRET_KEY` was rotated during Phase 0.
- **Paper upload**: `POST /api/v1/papers/upload` — validates MIME/extension, dedupes by SHA-256 checksum, enforces size limit, stores files under `uploads/papers/user-{id}/`, writes `UploadedPaper` row.
- **PDF extraction**: `extract_pdf_page_text()` in `app/services/paper_service.py` uses PyMuPDF, page-by-page text + metadata.
- **Chunking + embedding pipeline (Phase 1, complete)**: `chunking_service.py` does section-aware chunking with fallback to fixed-size+overlap. `embedding_service.py` runs chunks through Sentence Transformers and populates `document_embeddings`. A FAISS index is built and persisted to disk, updated incrementally on upload. `UploadedPaper.processing_status` moves through `uploaded → chunking → embedding → ready`/`failed`, triggered automatically as a background task after upload.
- **Retrieval + grounded chat (Phase 2, complete)**: hybrid search (FAISS + BM25) with cross-encoder re-ranking feeds retrieved chunks to the LLM. Chat endpoints (`POST /papers/{id}/chat`, `GET /papers/{id}/chat/{session_id}`) are live, scoped to `current_user.id`, and answers include page-level citations stored in `ChatMessage.citations` and surfaced in the UI.
- **LLM provider**: decided and wired up (Ollama local inference — see chat history/commits for the specific model if it matters going forward; the LLM call lives in an isolated service function so the provider can be swapped without touching retrieval/chunking/chat logic).
- **Summaries + concept explanations (Phase 3, complete)**: summary endpoint generates and caches a whole-paper summary (not regenerated on repeat requests). Concept explanation endpoint supports difficulty levels (beginner/intermediate/expert) via prompt variation. Both have working frontend UI on the paper detail page.
- **Multi-paper Q&A (Phase 4, complete)**: chat sessions can span multiple `paper_id`s, retrieval pulls from the combined chunk pool, answers reference which paper each citation came from.
- **Frontend redesign (Phase 5, complete)**: visual direction was chosen (clean/minimal) and applied across the homepage, dashboard, chat interface, and upload flow. Architecture page removed from user-facing nav. Citation labels are spelled out clearly (e.g. "Source 1, pages 1-2") rather than abbreviated.
- **Production polish (Phase 6, complete)**: evaluation harness exists (test papers + expected Q&A pairs + scoring script). Rate limiting is on LLM-calling endpoints with latency/cost logging. Dashboard shows real data, not placeholders.
- **Authorization**: every user-scoped resource (papers, chunks, embeddings, chat sessions) correctly scopes queries to `current_user.id`, following the pattern established in `get_user_paper_by_id`. Keep this pattern for every new resource added in Phase 19 onward.
- **Structured summary upgrade (Phase 16, complete)**: `summary_service.py` rewritten in place — this upgrades Phase 3's summary, it's not a second feature. `chunking_service.extract_outline_and_pages()` builds the "Contents" outline by reusing the same low-level font-size/bold detection chunking already uses, but with a *broader* heading predicate (`_is_outline_heading`, not the keyword-restricted `_is_heading` chunking relies on) — chunking only needs to find *a* split point, so missing a non-standard heading like "Model Architecture" was harmless there, but a real Contents view needs the paper's actual section titles. The broader predicate is filtered hard against the false positives that surfaces (prose sentences, figure/table captions, bare page numbers, author/affiliation blocks — dropped via "everything before the first keyword-matched heading is front-matter") — verified live down to a two-noise-entry residue on a real paper. Each outline section is summarized separately (map step) from its own chunks; the overall summary is then generated from those section summaries (reduce step) rather than sampled raw chunks, so long papers are covered evenly instead of by sampling. Equations are found heuristically (a standalone or trailing "(3)"-style numbered marker, backed by a short backward line-window to recover a fraction's numerator/operator/denominator split across lines by PDF layout reconstruction; a weaker Greek-letter/math-symbol density signal otherwise) and explained by the LLM in JSON mode (`generate_chat_completion(..., json_mode=True)`, new on `llm_service.py`), grounded in the surrounding chunk — the raw extracted text is always shown verbatim alongside the explanation, and an LLM LaTeX reconstruction (rendered via KaTeX) is always labeled as a reconstruction, never presented as the paper's exact formatting. Methods/algorithms/datasets are extracted the same JSON-mode way from the section summaries. Cached on new `UploadedPaper.structured_summary` (JSONB) + `summary_status` (pending/generating/ready/failed) + `summary_error` columns — the old plain-text `summary` column is left untouched but no longer written to; a cache hit requires `structured_summary.format_version` to match `SUMMARY_FORMAT_VERSION`, so old-format or stale summaries regenerate instead of being served as-is. Runs as a background task (many LLM calls per paper) with the status polled by the frontend, same pattern as paper processing; a prior failure only auto-retries on an explicit `refresh=true`, not on every page view. `summary_service.get_or_generate_summary()` (the old Phase 3 function signature) is kept as a synchronous back-compat shim purely so Phase 10's `/papers/compare` keeps working unmodified — it runs the same full pipeline synchronously on a cache miss and returns just the overall-summary string. Frontend: `SummaryPanel.tsx` rewritten — Contents list (links scroll to each section), collapsible per-section summaries (native `<details>`), overall summary, and an "Equations & methods" section with KaTeX-rendered reconstructions. Verified live on two real papers: "Attention Is All You Need" — outline matched its actual ToC near-exactly (Model Architecture, Why Self-Attention, Training, etc., not just the generic keyword set), the scaled dot-product attention equation was found (page 4) and correctly explained, methods list was accurate (Transformer, multi-head attention, Adam optimizer, byte-pair encoding, ...); a deliberately low-math AI-ethics paper — zero equations invented. A second request for the same paper returned in 0.16s with `cached: true`. `/papers/compare` was re-verified against both papers afterward with zero code changes on its side.
- **New-paper alerts (Phase 15, complete)**: a `notifications` table (`backend/alembic/versions/4f4f5d9d1f20_add_notifications.py`) with `source`/`external_id`/`title`/`message`/`categories`/`recommendation_score`/`is_read`. `notification_service.run_alert_job()` reuses Phase 14's `get_recommendations()` directly (no second profile mechanism) to find new candidate papers above `NOTIFICATION_SCORE_THRESHOLD` (0.35 default) and inserts a notification per new `(user, external_id)` pair, skipping ones already notified. Runs on an APScheduler `BackgroundScheduler` every `NOTIFICATION_CHECK_INTERVAL_HOURS` (4 default), wired into `main.py`'s FastAPI `lifespan`. `GET /notifications` (list + unread count), `POST /notifications/{id}/read`, `POST /notifications/check` (manual trigger, used for testing instead of waiting for the real interval). Frontend: `NotificationBell.tsx` in `AppLayout.tsx` — unread badge, dropdown list, mark-as-read. Verified live: manually triggered the job against a robotics/AI-skewed library (created 7 notifications, all `cs.RO`/`cs.AI`/`cs.LG` matching the actual interest profile), re-ran it and got 0 new notifications (0 duplicates), marked one read and confirmed both its `is_read` state and the unread count updated correctly.
- **Personalized recommendations (Phase 14, complete)**: `recommendation_service.build_interest_profile()` aggregates each library paper's categories (stored on `paper_metadata['categories']` at import time — `PaperImportRequest.categories`, validated against `ARXIV_CATEGORIES`), weighting recently-viewed papers 2x; a paper with no stored categories (e.g. a manual upload) falls back to classifying its title alone via Phase 13's classifier. `GET /papers/recommendations` takes the top 3 profile categories, fetches recent arXiv candidates via `external_paper_service.search_recent_category_papers()` (category-only, no keyword — exactly what Phase 12's arXiv integration already supports), scores each candidate by category-overlap with the profile (normalized by the top-3 categories' weight mass so the score reads as [0,1] regardless of how many categories the library spans), and excludes anything already in the library by `(source, external_id)`. Frontend: `RecommendationsPanel.tsx` on the dashboard, reusing the Phase 7 result-card + import pattern — no new card component. Verified live: imported 2 robotics papers, confirmed the interest profile correctly skewed `cs.RO`/`cs.AI`, confirmed every recommendation was genuinely relevant to that profile, and explicitly confirmed zero overlap between the imported papers' external IDs and the recommended set.
- **arXiv category classifier (Phase 13, complete)**: a TF-IDF + one-vs-rest logistic regression model trained on a stratified sample (80k train / 20k test) of Cornell's Kaggle arXiv-metadata dataset, predicting the same 9 categories as `ARXIV_CATEGORIES`. Exported to `backend/ml_models/category_classifier.joblib` + `category_vectorizer.joblib` (loaded once at import time by `classification_service.get_classification_service()`), with `evaluation_report.txt` recording per-category and macro-averaged precision/recall/F1 (macro F1 0.715) for the course report. `predict_categories(title, abstract, threshold)` is the only integration point Phases 14/15 call — they don't retrain or reimplement anything. Training provenance (`backend/train_locally.py` → `ml_models/convert_json_to_csv.py` → `ml_models/training_script_local_sampled.py`, verified with `backend/verify_classification.py`) is a local, sampled run rather than the Kaggle-notebook path `ml_models/README.md` documents as the primary route — a practical deviation from the original plan, not hidden: the raw ~11GB dataset is gitignored (`backend/ml_models/data/`), see the README for how to reproduce either way. Verified live: a robotics-titled paper classifies `cs.RO` at 0.9997; a Transformer-abstract paper classifies predominantly `cs.CL`/`cs.CV` — both sensible.

Every result (`ExternalPaperResult`) now carries a `categories` field: real arXiv category codes parsed from each entry's `<category>` tags for arXiv results, Semantic Scholar's own `fieldsOfStudy` as a secondary badge for its results — same shape either way, no separate taxonomy to reconcile. `GET /papers/categories` exposes the whitelist so the frontend doesn't hardcode a second copy. Frontend: multi-select category chips on `/discover` — selecting a category with no keyword typed searches immediately (recent-sorted); combining with a keyword narrows within it on explicit Search. - **Paper format review (Phase 17, complete)**: `format_templates.py` defines two templates as plain data (`imrad`, `ieee`) — each an ordered list of sections with `aliases` (for matching against Phase 16's outline headings), `required`, and an optional `word_range` (currently only Abstract). `format_review_service.py` matches a paper's actual outline to a template greedily in document order, then runs: a missing-required-section check, an out-of-order check (comparing matched sections' real page order against the template's declared order), an abstract word-range check, a near-empty-section check (skipped for Abstract, which has its own range check, and Keywords, which is expected to be short), a figure/table-caption-never-referenced check, an in-text-citation/reference-list cross-check (only attempted when the references section actually uses numbered-bracket style — an author-year paper is skipped silently rather than guessed at), and an equation-numbering-consistency check (reusing Phase 16's `summary_service.find_equation_candidates()` directly, via a small public wrapper added for this, rather than reimplementing detection). Four LLM qualitative checks (abstract states problem/approach/result, introduction has a real problem statement, methodology is detailed enough to follow, conclusion doesn't introduce new unsupported claims vs. the abstract as context) run in JSON mode, explicitly instructed not to re-flag what the deterministic checks already cover. Section text for both the deterministic word-count checks and the LLM checks is sliced starting at the heading's own position (not the whole page) and trimmed at the next section's heading or a footnote-marker line (∗/†/‡) — needed because a page-1 section's raw page text otherwise pulls in the title/author/affiliation block or footnote text ahead of/after it, which inflated the Abstract's measured length from a real ~170 words to 394 in testing before this trim was added. Cached per-template on `paper_metadata['format_review'][template_id]` (status pending/generating/ready/failed, same polling pattern as Phase 16) rather than a dedicated column, since several templates can have independent cached results for the same paper. New `UploadedPaper.is_user_authored` flag (set via a form field on the existing upload endpoint) distinguishes "my own paper" in the UI; it does not gate the feature itself — the review can run against any paper already in the library, same as the Phase 17 spec's own frontend bullet describes. `GET /papers/format-templates` exposes the template list; `GET /papers/{id}/format-review` polls (and auto-triggers once, like Phase 16's summary endpoint); `POST /papers/{id}/format-review` always force-regenerates. Frontend: `FormatReviewPanel.tsx` (template dropdown, run/regenerate button, section checklist, findings grouped by severity with page + fix) on a new "Check my paper" tab; a checkbox on the upload dropzone sets `is_user_authored`. Verified live: a real 11-page copy of "Attention Is All You Need" produced exactly one correct low-severity finding (inconsistent equation numbering) and zero false positives; a deliberately broken copy with the Conclusion/References pages stripped correctly flagged both as `missing` and nothing else; a direct test of the conclusion-LLM-check against a conclusion with a fabricated, unestablished benchmark number correctly flagged it with the right page; a second poll returned `cached: true`.
- **Translation (Phase 18, complete)**: `translation_service.py` wraps NLLB-200-distilled-600M (loaded once via `transformers.AutoModelForSeq2SeqLM`, not Ollama — see the Build Phases entry above for why) behind one `translate_text(text, target_lang)` function, paragraph-chunked (sentence-split within an over-long paragraph) so no single `generate()` call risks truncation, and decoded with beam search (`num_beams=4`) after greedy decoding was observed to silently drop a trailing sentence on some inputs. Citation markers/URLs/numbers are masked with reserved numeric placeholders (not letters — see the Build Phases entry for the two failure modes found and fixed) before translation and restored after. Three independent translation targets, each its own background job + pollable status nested in `paper_metadata` (never a new top-level DB column): the Phase 16 summary (`?lang=` on the existing summary endpoint), Phase 17 format-review findings (`?lang=` on the existing review endpoints), and the paper's own text section-by-section (new `GET/POST /papers/{id}/translate-section`). Concept explanations and chat answers translate synchronously instead (both were already synchronous, uncached, single-paragraph endpoints — adding one local-model call inline matches their existing design). `GET /papers/languages` exposes the whitelist (`{"hi": "Hindi"}` — only Hindi has actually been verified end-to-end, per this phase's own instruction not to list a language just because the model happens to support it). Frontend: `LanguageSelector.tsx` on the paper detail page (persisted via `localStorage`), threaded through `SummaryPanel`/`FormatReviewPanel`/`ConceptExplainPanel`/the chat send call; a "Translate" action per Contents entry for the paper's-own-text target; Noto Sans Devanagari loaded (Google Fonts) and scoped to a `.translated-text` class so only actually-translated content uses it. Verified live against real papers already in the library: a Hindi summary, a Hindi format-review finding, a Hindi section translation, and a Hindi chat answer were each read for meaning (not just "it's Devanagari") — see the Build Phases entry for specifics; every citation marker/number/equation checked matched the English original exactly; every translation target hit its cache on a second request; plain English requests (no `lang`) re-verified byte-for-byte unchanged from before this phase.

**Post-launch bug fixes (user-reported, both in `chunking_service.py`/`summary_service.py`):**
- **429s while a summary was generating**: `SummaryPanel.tsx` polled every 3s (20/min) against an endpoint limited to 10/min — a mismatch left over from when generation was synchronous (Phase 3); Phase 16 made it a multi-minute background task but the limit was never revisited. Fixed by raising the endpoint to 30/min and the poll interval to 8s. Also fixed a related latent bug found while in there: `refresh=true` could get permanently blocked if `summary_status` was ever orphaned at `"generating"` (e.g. a server restart mid-task) — restructured the trigger logic so an explicit refresh always fires regardless of current status, while plain polling still won't double-trigger.
- **Outline (`extract_outline_and_pages`) was showing every subsection, not just top-level ones**: the numbering-depth heuristic that was supposed to fold subsections into their parent had two bugs: (1) a keyword match (Abstract/Introduction/...) was incorrectly treated as establishing a numbering *scheme* for the rest of the document, so on a paper that never numbers its body sections, everything after the first keyword heading got wrongly demoted as "one level deeper"; (2) the prose-rejection word-count cutoff (8 words) was tight enough to drop real section titles ("The challenges of a principled approach to AI Ethics", 9 words) as "prose", silently orphaning that section's own numbered subsections with no parent to fold into; (3) a paragraph set a point or two larger than body text (a "teaser" style some templates use) was passing the heading size-ratio check, and lines that word-wrap mid-word ("the standard back-") were getting caught as heading candidates. Fixed all three (keyword matches no longer touch the numbering-depth tracker; cutoff raised to 12 words; added a mid-word-hyphen-wrap rejection) and re-verified against "Attention Is All You Need" (clean, unchanged), the AI-ethics paper (its real top-level sections restored), and the actual paper the user reported the bug against ("Embedding Prediction Helps Image Generation" — outline is now exactly Abstract/Introduction/Related Work/Method/Experiments/Conclusion/References/Future Work, matching what they asked for).
- **Equations were low quality**: `_find_candidate_equations`'s backward-scan (which recovers an equation's body from the lines before its trailing "(3)"-style marker) only stopped at *long* lines ending in a period, so short prose lead-ins ("...as follows:", "...defined as:") were getting pulled into the raw text fed to the LLM. Also, a trailing "(N)" isn't unique to equation numbering — multi-panel figure captions ("(a) Goldfish (1) (b) Bald eagle (22) ...") matched the identical shape and were being mistaken for equations, repeatedly, growing with each sub-label. Fixed by (1) stopping the backward scan at any line ending in `.`/`:`/`!`/`?` regardless of length, and (2) requiring at least one real math symbol/operator/Greek letter in the matched text before treating it as an equation at all. Also hardened `EQUATION_SYSTEM_PROMPT` against inventing unsupported terms (explicitly told to prefer `latex: null` over a plausible-looking guess) and dropped the equation-explanation call's temperature to 0.1. Verified live against the user's actual paper: the two "numbered" equations are now genuinely correct (e.g. `p = hθ(z), LNEPA = D(ztarget, p),` on page 3, correctly explained), and the figure-caption false positives are gone. Residual known limitation: when two separate numbered equations sit close together with no sentence-ending text between them, the backward scan can still merge them into one block, occasionally confusing the LLM's LaTeX reconstruction for that one entry — not fully solved, flagged here rather than silently left in.

### Phase 18 — Translation (Hindi first, multilingual-ready) ✅ complete
- ~~For users who aren't comfortable reading English...~~ Done — see "Already Implemented" above. DoD met: verified live on real papers already in the library — a Hindi summary (overall summary + section summaries + equation explanations) read as natural, correct Hindi with the right technical terms ("अत्याधुनिक" for "state-of-the-art", not a literal/wrong word), a format-review finding translated correctly with its fix suggestion, one "translate this section" (Abstract) call produced a coherent Hindi reading of the actual section text, and a Hindi chat answer kept its `[S1]` citation marker and every number exactly intact. A second request for every one of these hit the cache (`cached: true`, ~0.08s). Plain English requests (no `lang`) were re-verified byte-for-byte unchanged from before this phase.

**Translation backend decision**: the existing Ollama chat model (`llama3.2:3b`) was tried first, per this phase's own instruction, on a real summary paragraph — its Hindi had real quality problems: "state-of-the-art" came back as the nonsensical "राज्य-शीर्ष" (literally "state-top") instead of the correct "अत्याधुनिक", and "generator"/"generated" were mistranslated as "पीढ़ी" (a generation of people). NLLB-200-distilled-600M (Meta, local, CPU, ~2.4GB) was tried next on the identical sentence and got both right, with noticeably more natural grammar throughout — so translation is NOT routed through `llm_service`/Ollama at all; `translation_service.py` loads NLLB directly via `transformers`. IndicTrans2 (AI4Bharat) was considered too but not used: it requires a separate preprocessing toolkit (`IndicTransToolkit`) to get its documented quality, which was more integration risk than NLLB's plain `AutoTokenizer`/`AutoModelForSeq2SeqLM` path for the time available — a pragmatic choice, not a quality verdict between the two.

**What gets translated, and how it's cached**: three independent targets, each its own background job + pollable status (same `pending/generating/ready/failed` pattern as every other Phase 16-18 generation) —
- The Phase 16 structured summary (`overall_summary`, each section's heading+summary, each equation's `explanation` only — `raw_text`/`latex` are never even passed to the translator) via `?lang=hi` on the existing `GET /papers/{id}/summary`. Cached at `paper_metadata['translations'][lang]['summary']`, keyed to `summary_generated_at` so a re-generated English summary invalidates it.
- Phase 17 format-review `findings` (`section`/`message`/`fix`) via `?lang=hi` on the existing format-review endpoints. Cached at `paper_metadata['format_review'][template_id]['translations'][lang]`, keyed to that review's own `generated_at`.
- The paper's own text, section-by-section, on demand — new `GET/POST /papers/{id}/translate-section?section_index=N&lang=hi`, reusing Phase 16's outline for section boundaries and Phase 17's `format_review_service.slice_section_text()` (made public for this) to get clean section text. Cached at `paper_metadata['translations'][lang]['sections'][index]`, keyed to `paper.processed_at` (stable until the paper is ever re-processed).

Two targets are translated synchronously instead (no background task): concept explanations (`POST /papers/{id}/explain` with a `lang` field) and chat answers (`POST .../chat` with a `lang` field) — both already synchronous, uncached, single-short-paragraph endpoints before this phase, so adding one more local-model call inline matches their existing design rather than introducing a new poll flow for a few extra seconds of latency. Chat's stored `ChatMessage.content` stays English always; only a `translated_content` field is added to that one response — the next poll of the same session still shows English unless translation is requested again. The methods list in a summary is deliberately never translated (proper nouns like "Transformer" or "Adam optimizer" have no meaningful Hindi equivalent).

**Protecting citation markers/URLs/numbers — two failure modes found and fixed in testing, not assumed to just work**:
1. A placeholder scheme using repeated letters (`QQQ0QQQ`) was tried first and failed: NLLB is a *generative* model, not a literal find-and-replace, and repeated identical characters got corrupted in 2 of 3 multi-placeholder test sentences (an extra character appended in one case; a character silently dropped — breaking the restore regex entirely — in another). A bare number in a reserved, implausible-in-prose range (9000000+index) was tried next and survived perfectly across every test, since NLLB already reliably passes real numbers through untouched on its own — reusing that same proven path for placeholders, instead of inventing a new token class, is what actually works.
2. Two citation markers directly adjacent with no space (`[S1][S2]` — this app's own standard multi-citation style, see `citation_utils.CITATION_INSTRUCTION`) mask to two touching placeholder numbers that merge into one ambiguous digit blob the unmask regex can't separate. Fixed by inserting a single space between two placeholders that would otherwise land adjacent (`_mask_protected_spans` in `translation_service.py`) — the one cosmetic side effect, "[S1] [S2]" instead of "[S1][S2]", was accepted as a reasonable trade for both markers surviving at all.
3. Separately, greedy decoding (`num_beams=1`, the `generate()` default) was observed to silently drop a trailing sentence on some masked inputs rather than translating it — switched to beam search (`num_beams=4`, ~1.8x slower on CPU, ~3s per chunk) after confirming it reliably produced the complete translation in every case tried.

**Known residual limitations, not chased further given scope**: a markdown-style bullet list inside a chat answer (lines separated by single `\n`, not `\n\n`) gets flattened onto one line by translation, since chunking only splits on paragraph breaks — numbers/citations inside it are still exactly correct, only the line-break layout is lost. A translated paper section can occasionally pull in a trailing bare-digit footnote marker the same way the pre-fix equation extractor once did for ∗/†/‡ markers (not yet extended to plain-digit footnotes).

- **arXiv returns 406 to TLS connections that negotiate ALPN `http/1.1` on cache-miss requests** (proved with raw sockets — identical bytes, ALPN on → 406, off → 200). `external_paper_service._http_client()` supplies an SSL context whose `set_alpn_protocols` is a no-op — don't construct bare `httpx.Client`s for external calls, use `_http_client(settings)`. Cache hits mask this, so it looks intermittent when testing.
- `bcrypt` is pinned `<4.1` in `pyproject.toml`: passlib 1.7.4 breaks on bcrypt ≥5 (every hash/verify raises the 72-byte error) and logs a noisy warning on 4.1+.
- **`generate_chat_completion(messages, json_mode=True)`** (`llm_service.py`, added in Phase 16) asks Ollama for JSON-constrained output — use it for any new structured-extraction prompt (Phase 17's format-review findings will want this) rather than parsing free text or re-inventing the option. Still validate/guard the parse (`json.loads` + type checks) — json_mode makes the *shape* reliable, not the *content*.
- **`chunking_service._is_heading` (keyword-restricted) vs `_is_outline_heading` (broad, visual-only)** are deliberately two different predicates sharing one `_extract_pages_and_headings(pdf_path, heading_predicate=...)` function. Don't merge them: chunking only needs *a* split point (a missed non-standard heading is harmless there), but the outline needs the paper's actual section titles, which requires accepting any heading-shaped line and then filtering hard against prose/captions/page-furniture — a materially different risk trade-off, not just a stricter version of the same rule.
- **A matched section's raw page text is not its actual text** — a page's `get_text("text")` includes whatever else shares that page (title/author/affiliation block before a page-1 Abstract, footnote markers after it, the next section's heading if it starts on the same last page). `format_review_service._slice_section_text()` trims to the heading's own position and the next matched section's heading / a footnote-marker line (∗/†/‡); skipping this trim is what let the Abstract word-count check overcount by more than 2x in testing. Any future feature that needs "just this section's text" from Phase 16's outline should reuse this helper, not re-slice page text from scratch.
- **`summary_service.find_equation_candidates()`** is a thin public wrapper around the private `_find_candidate_equations` purely so Phase 17's equation-numbering-consistency check could reuse the exact same detection logic without a cross-module underscore-prefixed import. Add new equation-detection logic there, not a second copy in `format_review_service.py`.
- **`translation_service.translate_text()` protects citation markers/URLs/numbers with reserved numeric placeholders (9000000+index), not letters.** A letter-based placeholder was tried first and failed under NLLB's generation in 2 of 3 test sentences (one got an extra character appended, one got a character silently dropped — which broke the restore regex entirely, since translation is generative, not a literal passthrough). If a future language is added to the whitelist, verify this masking still holds for that language too before trusting it — it was only empirically verified for Hindi/NLLB-200.
- Phase 19 (live demo readiness) is a pre-demo checklist to run through shortly before an actual scheduled demo, not a feature to build once and forget — re-verify it close to demo day.
