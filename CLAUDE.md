# AI Research Paper Assistant

## Project Purpose
Portfolio project for backend/AI-engineering internship applications. Users upload research papers (PDF), and the system uses RAG (Retrieval-Augmented Generation) to summarize them, answer questions grounded in the paper's actual content, and explain difficult concepts at different depths.

**Phases 0 through 12 are COMPLETE. This file has been updated to reflect that — do not treat language like "not yet added" or "decide before Phase 2" as still open; those decisions were already made and built. If you find code that contradicts what's described below as done, flag the mismatch to the user rather than silently assuming the file is right — the file may not perfectly reflect every implementation detail, but the core pipeline described here is built and working.**

**Bug found and fixed (during Phase 11 verification): `UploadedPaper.chat_sessions` (`app/models/uploaded_paper.py`) was declared with `cascade="all, delete-orphan"`. Deleting a paper that anchors a chat session cascade-deleted that session (and all its messages) at the ORM level — even a multi-paper (Phase 4) session with other papers still very much alive in the library — directly contradicting `delete_uploaded_paper`'s own docstring, which claims the anchor is set to NULL by the FK's `ondelete="SET NULL"` and the session survives. The ORM-level cascade was pre-empting that FK before it ever got a chance to apply. Fixed by dropping the cascade from that one relationship. Verified live with the exact failure scenario: created a session anchored on Paper A but also linked to Paper B (Phase 4 multi-paper), deleted Paper A, confirmed via direct DB query and the actual `GET /papers/{B}/chat/{session_id}` API call that the session survived with its anchor nulled, its link to Paper B intact, and both messages preserved.**

### Phase 13 — Train + export a paper category classifier (Kaggle)
This phase produces the model that Phases 14 and 15 depend on. Do not start 14 or 15 before this is done and the exported model is loadable in the backend.

- **Dataset**: Cornell University's arXiv Metadata dataset on Kaggle (`Cornell-University/arxiv`) — ~2.2M+ papers with title, abstract, and categories. Use the same category set already in use for Phase 12's filter (`cs.LG`, `cs.AI`, `cs.CV`, `cs.RO`, `cs.CL`, `stat.ML`, etc., i.e. the `ARXIV_CATEGORIES` whitelist in `external_paper_service.py`) — don't invent a different taxonomy.
- **Task**: multi-label classification — given a title + abstract, predict which categories it belongs to (a paper can have more than one).
- **Training environment**: a Kaggle notebook (free GPU available if using a transformer). Start with a TF-IDF + logistic regression (one-vs-rest) baseline — fast to train, easy to explain, good enough to ship. Only move to a fine-tuned small transformer (e.g. DistilBERT) if there's time and the baseline's metrics are genuinely weak; don't add model complexity the report can't justify.
- **Evaluation**: report precision/recall/F1 per category and macro-averaged, on a held-out split. This is a real deliverable for the course report, not just an internal check — keep the notebook's evaluation cell output as part of your submission materials.
- **Export**: save the trained model in a format the FastAPI backend can load directly — `joblib` for the TF-IDF+logistic-regression baseline (small, no extra runtime dependency beyond scikit-learn), or the model's `state_dict` + tokenizer config if a transformer was used. Download the exported artifact from Kaggle and commit it under a new `backend/ml_models/` directory (or store it outside git with a documented download step if it's large — decide based on actual file size once trained).
- **Backend integration**: new service `classification_service.py` that loads the exported model once at startup and exposes a `predict_categories(title, abstract) -> list[(category, score)]` function. This is the only integration point — Phases 14 and 15 both call this function, they don't retrain or reimplement anything.
- DoD: `predict_categories()` returns sensible category predictions for a handful of real, known papers (e.g. run it against a couple of papers already in the user's library and confirm the predicted categories roughly match arXiv's actual listed categories for them); evaluation metrics are recorded somewhere durable (notebook output, or a short `ml_models/README.md` summarizing them) for the course report.

## Working Notes for Claude Code
- **`uvicorn --reload` does not work on this machine** (Python 3.14 + Windows): it logs "Reloading..." but never replaces the worker, so the old code keeps serving and orphaned workers can survive a parent kill. Run the backend with `python -m uvicorn app.main:app --port 8000` (no `--reload`) and restart it manually after code changes; check `Get-NetTCPConnection -LocalPort 8000 -State Listen` shows exactly one owner.
- **arXiv returns 406 to TLS connections that negotiate ALPN `http/1.1` on cache-miss requests** (proved with raw sockets — identical bytes, ALPN on → 406, off → 200). httpx/httpcore always sets that ALPN; `external_paper_service._http_client()` supplies an SSL context whose `set_alpn_protocols` is a no-op. Don't construct bare `httpx.Client`s for external calls. Cache hits mask this, so it looks intermittent when testing.
- `bcrypt` is pinned `<4.1` in `pyproject.toml`: passlib 1.7.4 breaks on bcrypt ≥5 (every hash/verify raises the 72-byte error) and logs a noisy warning on 4.1+.
- **Phases 0-12 are complete.** Read the "Already Implemented" section above as ground truth. If actual code contradicts it, flag the specific mismatch to the user rather than silently rebuilding or assuming the file is wrong.
- Read this file plus the actual current code before starting Phase 13 — get familiar with the existing chunking/embedding/retrieval/chat/discover services before adding new features on top of them.
- After each phase, report exact manual verification steps/commands, and don't proceed to the next phase until those are confirmed working.
- Phases 14 (recommendations) and 15 (alerts) both depend on Phase 13 (trained classifier) — do not start either before Phase 13's model is loadable in the backend.
