# Evaluation harness

A small, fixed set of hand-written question/answer pairs, run against the
real backend over HTTP (same path the frontend uses), scored for keyword
coverage, citation page accuracy, and honest "I don't know" behavior on
questions the source papers don't answer.

## Run it

Backend must be running first:

```bash
cd backend
uvicorn app.main:app
```

Then, in another terminal:

```bash
cd backend
python eval/run_eval.py
```

Point it at a different backend with `--base-url`.

## What it does

1. Logs into (or registers, on first run) a dedicated eval account
   (`eval-harness@example.com`) — kept separate from real user data.
2. Uploads the fixture papers in `fixtures/` if not already present
   (checksum-matched, so re-runs don't re-upload) and waits for each to
   finish processing.
3. Asks each question in `dataset.json` through a **fresh chat session**
   (never reused across cases, so one question's context can't leak into
   another's grading) via `POST /papers/{id}/chat` — the exact endpoint the
   UI calls.
4. Scores each answer:
   - **Keyword coverage** — for questions with a known answer, checks that
     each expected fact appears (as any of several acceptable phrasings, to
     tolerate paraphrasing rather than requiring exact wording).
   - **Citation accuracy** — checks that at least one citation lands on the
     expected page(s) of the source PDF.
   - **Honest refusal** — for the "not mentioned in the paper" questions,
     checks the answer actually hedges (contains a phrase like "don't know" /
     "not mentioned") rather than fabricating an answer.
   - **Multi-paper attribution** — the comparison question checks that
     citations from *both* source papers appear, not just one.
5. Prints a pass/fail summary and writes the full detail to `report.json`.

## Files

- `fixtures/*.pdf` — two short synthetic papers with clearly verifiable
  facts (numbers, named techniques) chosen specifically so the expected
  answer is unambiguous and machine-gradable. Generated by
  `generate_fixtures.py`; committed so the fixture content is stable across
  runs. Re-run that script only if you want to change the fixture content
  itself.
- `dataset.json` — the question/expected-answer pairs.
- `run_eval.py` — the runner.
- `report.json` — written by the last run (gitignored — it's output, not
  fixture data).

## Regenerating fixtures

Only needed if you want different fixture content:

```bash
python eval/generate_fixtures.py
```

This overwrites `fixtures/*.pdf`. If you do this, the eval account's
previously-uploaded papers won't match the new checksums, so the next
`run_eval.py` will upload the new versions as additional papers under the
eval account rather than replacing the old ones — clean up the eval
account's old papers first if you want a clean slate (via the dashboard, or
`DELETE /papers/{id}`, logged in as the eval account).
